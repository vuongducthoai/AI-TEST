§1  Khi nào Single Agent thất bại?

ReAct — mạnh nhưng không biết sửa lỗi.

Thoughtsuy luận→ Actiongọi tool→ Observationkết quả↺ lặp đến khi có câu trả lời

ReAct = “Think before you act” — mỗi bước agent giải thích lý do trước khi hành động.

3 failure modes của ReAct

1 · Lỗi lan tỏaSai ở bước 1 → sai hết chuỗi.
2 · Infinite loopTool trả noise → agent lặp mãi.
3 · Không backtrackĐi sai đường nhưng không quay lại.
Root causeReAct không có cơ chế tự đánh giá. Khi đi sai, không có signal nào báo “dừng lại, suy nghĩ lại”.

Case study: lỗi lan tỏa trong PR review

  1. Agent đọc nhầm module trong diff — hiểu sai file nào thực sự bị đổi
  2. Agent chạy checker/search trên các file không liên quan
  3. Agent tổng hợp bằng chứng sai nhưng vẫn trình bày với độ tự tin cao
  4. ReAct không có signal nào để dừng lại — không ai chấm điểm bước giữa chừng

Evaluator giải quyết được vì nó chấm được: “kết luận có grounded vào diff thật và test logs thật hay không?”

Đừng nâng cấp agent quá sớm

Nhiều tác vụ chỉ cần

  • Retrieval — tìm thông tin liên quan
  • Tools — gọi API/function có sẵn
  • Structured output — trả đúng format

Chỉ escalate khi gặp 1 trong 3

  • Tool overload — quá nhiều tool, 1 agent không quản nổi
  • Branching logic — prompt phải rẽ nhánh phức tạp
  • Specialist ownership — cần agent “sở hữu” riêng một domain
Bẫy“Càng nhiều agent càng tốt” là ngộ nhận — mỗi agent thêm vào là thêm latency, cost, và điểm lỗi mới. Chỉ thêm agent khi có evidence, không phải vì “nghe cool”.

§2  Reflexion — dạy Agent tự phản tỉnh critic layer

Shinn et al. 2023 — thêm Evaluator (đánh giá) và Reflector (rút bài học) vào ReAct.

1. GenerateActor→ 2. EvaluateEvaluator · score 0/1→ 3. ReflectReflector · rút bài học→ 4. RetryActor ↺ Reflection Memory
AnalogyNhư sinh viên làm bài thi — lần 1 sai → xem đáp án, hiểu tại sao sai → lần 2 làm đúng. ReAct chỉ làm 1 lần rồi nộp; Reflexion cho phép “xem lại bài” và sửa.

Điểm khác biệt vs ReAct: dùng text feedback thay gradient. LLM đã train trên ngôn ngữ tự nhiên → critique bằng text là “natural modality”.

Reflexion dùng episodic memory — agent “nhớ” bài học từ các lần thử trước trong cùng episode.

Thiết kế Evaluator prompt — 4 nguyên tắc

  1. Rubric tường minh — liệt kê tiêu chí cụ thể (đúng định dạng? đủ bước? khớp constraint nào?) thay vì hỏi chung chung “câu trả lời này tốt không?”
  2. Bắt buộc trích dẫn bằng chứng — chỉ ra đúng dòng/đoạn output nào khiến nó chấm như vậy
  3. Verdict máy đọc được — JSON {score, reason, evidence} để Reflector và code điều phối parse được
  4. Tách context với Actor — evaluator không được thấy lý do biện minh của Actor, nếu không dễ bị “thuyết phục”
Evaluator là mắt xích yếu nhấtNếu nó chấm sai, cả vòng lặp Reflect–Retry đi sai hướng. Dùng chung context với Actor = mất tính độc lập → nguồn gốc của correlated failure.

Reflection memory — ghi gì, bỏ gì?

✔ Lưu

  • Bài học rút ra: “thử X không được vì Y, lần sau thử Z” — cô đọng, hành động được
  • Chiến lược đã thất bại: để Reflector không đề xuất lại chính hướng đó
  • Ràng buộc mới phát hiện: constraint task không nói rõ nhưng attempt trước đã lộ ra

✘ Không lưu

  • Lịch sử chat thô của attempt cũ — chỉ tốn token, không tăng khả năng sửa lỗi
  • Tool dump đầy đủ (raw JSON, log request/response) — chỉ phần kết luận mới đáng giữ
  • Diễn giải lại task — không thêm thông tin mới

§3  Bức tranh rộng hơn search layer

LATS — khi cần tìm đường tối ưu

LATS = MCTS + LLM: mỗi node là một trạng thái suy luận; LLM đóng vai policy + value + simulation. UCT chọn nhánh tốt.

Đặc điểmChi tiết
Độ chính xácChính xác hơn Reflexion (92.7% vs 91%)
Chi phíTốn gấp 3–5× compute
Điều kiệnCần environment cho phép undo
Công thứcToT + Reflexion → LATS: ToT chỉ expand cây, Reflexion chỉ reflect — LATS làm cả hai cộng MCTS search
Khi nào đáng dùngChỉ với task giá trị cao, cho phép rollback (code gen, game). Thêm vào khi failure mode là “đi sai một nhánh, không quay lại được” — failure mode thứ 3 ở §1. arXiv:2310.04406

PRM vs ORM — chấm từng bước

ORM (outcome reward model)

Chỉ biết đáp án cuối đúng/sai — không biết bước nào đã sai. Chỉ biết sau khi đã đi hết B3.

PRM (process reward model)

Chấm từng bước suy luận, bắt lỗi sớm ở B2 ngay khi nó xảy ra, trước khi lan sang bước sau.

Thinking verifier (ThinkPRM, 2025): sinh verification chain-of-thought cho mỗi bước thay vì chỉ gán một điểm số rời rạc — đạt hiệu năng mạnh với ít hơn nhiều bậc độ lớn nhãn huấn luyện so với PRM discriminative.

Voyager — agent tích lũy kỹ năng

Auto Curriculumtự đặt mục tiêu→ task → Code Generator→ Verify & Debug→ verified skill → Skill Library (DB)↺ retrieve skills

Skill mới xây trên skill cũ (compound learning). Pattern áp dụng cho code generation, DevOps automation — bất kỳ domain nào agent cần tích lũy “thư viện kinh nghiệm”. Wang et al., 2023

Đường cong chi phí — cái giá của “search thêm”

Diminishing returns đến rất nhanh① Accuracy tăng theo test-time compute nhưng chững lại nhanh. ② Latency variance nới rộng — outlier ngày càng xa trung vị. ③ Chi phí hạ tầng có điểm không còn justify được accuracy gain nhỏ dần.
→ Hướng nghiên cứu đúng không phải “search nhiều hơn” mà là compute-efficient reasoning. arXiv:2506.04301

§4  Tích luỹ kỹ năng skill layer

Skill Library của Voyager tái xuất hiện 2026 dưới dạng skill files.

Skill files (on-demand)

Kiến thức domain chi tiết, chỉ load khi task chạm đến — nạp progressive, không nhồi hết vào context từ đầu. Giống Skill Library retrieve theo Auto Curriculum.

Persistent instruction file

Đọc một lần lúc khởi động (agents-file, kiểu CLAUDE.md) — áp dụng luôn, không đợi task chạm tới.

Không đo được thì không được tiến hoá

DGM không tin biến thể nào cả — mọi lần tự sửa code đều phải chạy qua benchmark, không qua thì bị loại. Eval harness là điều kiện tiên quyết để được phép tiến hoá.

  • Chấm tự động bằng verifier — hàng trăm biến thể, không chấm bằng người được
  • Regression set bắt buộc — biến thể mới không được phá kỹ năng cũ
  • Kiểm tra tính chuyển được — validate trên nhiều task/model để phân biệt cải tiến thật với overfit
  • Trace hợp lệ trước đã — không có trace chuẩn từ middleware (§7) thì không chấm được chiều nào
Cảnh báoMetric yếu thì agent tiến hoá theo metric, không theo mục tiêu — evaluator (§2) ở đây thành hàm mục tiêu của cả quá trình, sai lệch bị khuếch đại qua từng thế hệ.

§6  Plan — Act — Verify

Tách ba pha thay vì một vòng lặp “think then do” undifferentiated.

Plan→ Act→ Verify↺ sai → replan

Mỗi pha có một prompt riêng, một budget compute riêng, một tín hiệu thất bại riêng. Kết quả: pha nào hỏng, biết ngay pha đó — không phải đoán lại từ một transcript lẫn lộn cả ba việc.

Ba tín hiệu, không phải mộtPlan thất bại (mục tiêu sai) · Act thất bại (tool lỗi) · Verify thất bại (không đạt tiêu chí) là ba loại lỗi khác nhau — trộn chung vào một prompt xoá mất sự phân biệt này.
Không miễn phíMỗi pha là một lượt gọi model riêng — đổi latency lấy sự ổn định và khả năng debug.

Vì sao plan file thắng plan trong context?

Plan trong context

  • Bị drift: mỗi lần viết lại, chi tiết cũ có thể bị bỏ sót
  • Không diff được giữa hai turn
  • Mất trắng nếu context bị compact

Plan file trên đĩa

  • Addressable: mỗi mục có vị trí cố định
  • Diffable: so sánh hai thời điểm biết chính xác đã đổi gì
  • Sống sót qua compaction: nằm ngoài context window

Một harness có ba núm xoay

NúmĐặc điểm

Sáu hook — theo đúng thứ tự

1
before_agent

Chạy một lần khi agent khởi động — khởi tạo hạn mức (token, tool call, vòng lặp, thời gian), mở root span, gắn run-id

2
before_model

Quyết định model được thấy gì — context summarisation (nén cái đã dài) + context injection (nạp skill file, chèn lại plan file, chèn reflection memory)

3
wrap_model_call

Bọc bản thân lời gọi — retry, fallback, latency/cost

4
after_model

Nói về nội dung — critic layer của §2: Evaluator chấm output, Reflector sinh bài học, vòng thử lại. Cộng: validate schema, redact PII, phát hiện mẫu bất thường, đếm ngân sách

5
wrap_tool_call

Chạy cả trước lẫn sau lời gọi tool — gating (chặn/đổi tham số/trả lỗi trước mọi side effect), injecting context (tenant/user, scope, request-id), intercepting results (redact PII, cắt output khổng lồ, offload ra file)

6
after_agent

Chạy một lần khi kết thúc — chốt sổ ngân sách (tổng token, tổng cost, đã chạm trần nào), đóng span, gắn kết quả

Gom lạicritic layer (§2) = after_model · skill layer (§4) = nạp skill file ở before_model · search layer (§3) = điều khiển quanh wrap_model_call · deep-agent context (§6) = before_model + wrap_tool_call. Không cái nào là “kiến trúc đối thủ”.
Vì sao không đặt luật ở prompt?“Đừng gọi tool xoá khi chưa xác nhận” trong system prompt là một lời đề nghị; cùng luật đó trong wrap_tool_call là một bất biến.

Doom loop — đóng lại câu hỏi bỏ ngỏ ở §1

Failure mode thứ hai của ReAct (infinite loop) đến giờ vẫn chưa được giải quyết — Reflexion chấm chất lượng, không chấm sự lặp lại.

Vì sao model không tự thấy? Từ bên trong context, vòng lặp thứ N trông y hệt vòng thứ nhất. Sự lặp lại là thuộc tính của lịch sử — mà lịch sử đó có thể đã bị nén mất. Middleware thì thấy, vì nó giữ state qua các vòng.

Dấu hiệu: cùng tool + cùng tham số lặp quá N lần · hành động quay về đúng trạng thái cũ · plan file không đổi nhiều vòng liền.

4 cách phá — theo thứ tự leo thang:

  1. before_model — cảnh báo vào context: “đã thử cách này N lần, không tiến triển”
  2. wrap_tool_call — chặn hành động lặp, buộc agent đổi cách
  3. after_model — ép đổi chiến lược: không chấp nhận output với tiêu chí “lặp lại”
  4. after_agent — dừng và bàn giao: hết ngân sách → dừng có kiểm soát, trả trace

Compaction vs Truncation vs Eviction

Compaction

  • Một LLM viết lại toàn bộ lịch sử thành bản tóm tắt holistic
  • Giữ thông tin theo semantic relevance — chi tiết quan trọng từ đầu hội thoại vẫn giữ được
  • Lossy: chi tiết bị paraphrase, có thể trôi nghĩa
  • Tốn một lượt gọi model — có latency và chi phí riêng

Structured eviction

  • Xoá theo luật cố định — vd. tool result cũ hơn N lượt, hoặc output đã offload ra file (§6)
  • Rẻ: không gọi model, chỉ áp một điều kiện
  • Dự đoán được: biết trước chính xác cái gì bị bỏ, khi nào
  • Không cứu được thông tin rải rác giữa lịch sử

Truncation cắt theo vị trí — luôn mất phần cũ nhất, kể cả khi phần đó vẫn còn quan trọng. Đó là lý do compaction dùng LLM chứ không cắt cứng.

§9  Orchestrator — Worker subagent layer

  • Orchestrator tách task thành các phần việc con, giao mỗi phần cho một subagent
  • Mỗi worker chạy với context window cô lập — không thấy transcript của worker khác hay của orchestrator
  • Worker không trả nguyên transcript — chỉ một bản tóm tắt cô đọng, khoảng 1.000–2.000 token
  • Đây chính là subagent spawning ở §6, nhìn ở quy mô một hệ nhiều agent

Kinh tế học của multi-agent

Khi CHƯA cần multi-agent

  • Một agent đơn với tool tốt vẫn thắng — ít moving part, dễ debug
  • Task vừa đủ trong một context window
  • Chi phí điều phối chi phối: orchestrator + N worker = N+1 lượt gọi model cho một việc một agent làm được
  • Debug khó hơn: lỗi có thể nằm ở điều phối, không ở bất kỳ worker nào

Khi multi-agent bắt đầu đáng tiền

  • Quá tải tool: tách theo chuyên môn giảm nhiễu lựa chọn
  • Subtask song song thật sự — không phụ thuộc kết quả của nhau
  • Chuyên môn hoá theo chủ sở hữu: mỗi worker sở hữu một domain, bộ tool riêng, tiêu chí đúng/sai riêng
  • Cô lập context là mục đích, không phải tác dụng phụ — worker ô nhiễm không lan sang worker khác

§10  Guardrails & Capability Control

§7 đã hứa: guardrails gắn vào wrap_tool_call — đến lúc trả lời tại sao.

Bề mặt tấn công mớiPrompt injection là LLM01 — hạng mục đứng đầu OWASP Top 10 for LLM Applications ở cả bản 2023 lẫn 2025. Agentic AI cộng thêm kết nối tool/MCP mở ra bề mặt tấn công mới.
Kiểu tấn côngMô tả
Tool poisoningMetadata hoặc mô tả tool bị chỉnh sửa để dụ agent gọi sai
Credential theft qua tool outputOutput tool trả về chứa lệnh ẩn đánh cắp secret trong context
Indirect injection qua retrieved contentTài liệu/RAG chunk mang chỉ thị giả trang bị như dữ liệu thường

Defence in Depth — 5 lớp

  1. Validate input trước khi model nhìn thấy nó — lọc chỉ thị lạ ở tầng vào
  2. Validate output trước khi nó kích hoạt hành động
  3. Enforce permission qua capability manifest tại tầng tool-call — chính là hook wrap_tool_call (§7)
  4. Gate hành động không thể hoàn tác bằng một blocking pause chờ con người duyệt
  5. Giới hạn budget & action rate như circuit breaker cứng — chặn cứng, không phải gợi ý
Nguyên tắc bất di bất dịch“Một rule chỉ tồn tại trong system prompt không phải một lớp phòng thủ.” Model có thể bị thuyết phục bỏ qua một câu instruction — nhưng không thể bỏ qua một allowlist chặn cứng ở tầng infrastructure.

Mọi tool có thể gọi cần đủ ba thứ: scope định nghĩa rõ · allowlist entry · reversibility classification (có rollback được không).
